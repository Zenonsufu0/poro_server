# 역할 / 권한 정책 (SoT)

> 봇의 역할·권한 정책 단일 진실원. 코드: `core/config.py`, `core/permissions.py`,
> `modules/roles/role_commands.py`, `modules/onboarding/panels.py`,
> `modules/server_lifecycle/commands.py`.
> 도메인 문서(RPG 등)의 역할 서술과 충돌하면 **이 문서가 우선**한다.

## 대원칙

1. **권한 역할(운영 제어)과 알림 역할(플레이어 선택)을 분리한다.**
2. **운영 권한 역할은 수동 지급 전용이다.** 봇은 버튼·이모지·자동 로직으로
   운영 권한 역할을 절대 지급하지 않는다.
3. **운영 권한이 없는 자기선택 역할만 자동 지급한다.** 알림 역할(토글)·카테고리 접근
   역할(이모지)이 이에 해당한다. 이들 역할에는 어떤 운영 권한도 없다.
4. **공통 디스코드 인증과 서버별 화이트리스트를 분리한다(DL-131).** 화이트리스트는
   약관동의 + 인게임 본인인증을 거친 서버에만 부여한다. 공통 인증만으로는 어떤
   게임 서버에도 접속할 수 없다.
5. **카테고리 접근(가시성)과 화이트리스트는 별개다(DL-132).** 이모지로 받는 카테고리
   접근 역할은 해당 서버 카테고리(약관 채널 포함)를 **보이게만** 한다. 실제 게임 접속
   권한(화이트리스트)은 그 안에서 약관동의 + 인게임 인증을 마쳐야 부여된다.

## 역할 분류

### A. active 서버 온보딩 역할 (도메인 비종속 · 시스템 자동 승급)

현재 온보딩은 전역 active 서버 1개 모델이다. 서버 신설 시 생성된 3역할을
`modules/server_lifecycle/commands.py`와 `modules/onboarding/panels.py`가 사용한다.
구 `미인증`·`접속대기`·`인증유저` 전역 env 역할은 DL-138 이후 deprecated이며 optional이다.

| 역할 | 부여 시점 | 처리 코드 |
|---|---|---|
| 접근/임시 역할 | 디스코드 입장 직후 active 서버 자동 배정 | `modules/server_lifecycle/commands.py` |
| 인증전 역할 | 약관 동의 버튼 클릭 | `modules/onboarding/panels.py` |
| 플레이어 역할 | 인게임 `/인증` 코드 검증 성공 | `modules/onboarding/panels.py` + `integrations/*_api.py` |

> 닉네임 수동 입력은 폐기됐다. 게임서버가 발급한 `/인증` 코드 검증 응답의 `uuid`/`name`을
> 표시·로깅용으로만 사용하고, 매핑 권위는 게임서버에 둔다.

### A-2. 카테고리 접근 역할 (전역 active 자동 배정 · DL-132/T10 폐기 반영)

RPG·Zenon Mon을 동시에 운영하지 않는 전역 active 서버 1개 모델이므로, 이모지 서버선택은
폐기됐다. 신규 유저는 현재 active 서버의 접근 역할을 자동으로 받는다. 디스코드 채널 권한은
이 역할에게만 해당 카테고리(약관 채널·정보 채널 등)를 노출한다.

| 역할 | 부여 방식 | 효과 |
|---|---|---|
| `<도메인>접근` | active 서버 자동 배정 | active 서버 카테고리 가시화 |

> 운영 권한 없는 접근 역할이므로 자동 부여 가능(대원칙 ③).
> **카테고리 접근 ≠ 화이트리스트**(대원칙 ⑤). 카테고리가 보여도 게임 접속하려면 §D
> 서버별 약관동의 + 인게임 인증이 필요하다.
> 새 게임/서버는 `/서버신설`로 카테고리 + 3역할 세트를 만들고, active 전환 시 자동 배정한다.
> 구 이모지 서버선택 구현은 T10 폐기 상태다.

### B. 운영 권한 역할 (수동 지급 전용 — 봇 자동 지급 금지)

`config.PERMISSION_ROLE_IDS`. 운영진이 디스코드에서 직접 부여한다.

| 키 | 역할 | 비고 |
|---|---|---|
| `owner` | Owner | 슈퍼유저 — 모든 권한 통과 |
| `admin` | Admin | 관리자급 운영 명령 |
| `rpg_manager` | RPG Manager | RPG 운영(골드 지급 등) |
| `zenon_mon_manager` | Zenon Mon Manager | Zenon Mon 운영 |
| `event_manager` | Event Manager | 이벤트 등록/관리 |
| `support` | Support | 문의/지원 |

권한 체크: `core/permissions.py`
- `member_has_permission(member, *keys)` — 보유 여부(Owner 항상 통과)
- `is_admin(member)` — owner/admin 여부
- `@requires_permission("admin", ...)` — 슬래시 커맨드 데코레이터.
  권한 역할이 전부 미설정(0)이면 보수적으로 **차단**한다(무방비 노출 방지).

### C. 알림 역할 (자동 지급 가능 — 플레이어 토글)

`config.NOTIFY_ROLE_IDS`. `/알림설정` 버튼으로 자유롭게 추가/제거. 미설정(0)이면 버튼 숨김.

| 키 | 표시명 | 알림 대상 |
|---|---|---|
| `필드보스알림` | 필드보스 알림 | RPG 필드보스 5분 전·등장 |
| `시즌보스알림` | 시즌보스 알림 | RPG 시즌보스 모집·공지 |
| `월드보스알림` | 월드보스 알림 | 월드보스(서버 공통) |
| `포로몬알림` | Zenon Mon 알림 | Zenon Mon 이벤트/공지 |
| `이벤트알림` | 이벤트 알림 | 서버 이벤트 시작/종료 |
| `점검알림` | 점검 알림 | 점검 안내 |
| `업데이트알림` | 업데이트 알림 | 패치/업데이트 공지 |

> 클래스 역할(`config.CLASS_ROLE_IDS`: 검사/도끼전사/…)은 RPG 도메인 전용 선택 역할이다.
> 1인 1클래스, `/클래스선택`. 상세는 [`domains/rpg.md`](domains/rpg.md).

### D. 서버별 화이트리스트(플레이어) 역할 (서버별 약관동의 + 인게임 인증)

공통 인증(§A)을 마친 유저에게 **각 게임 서버의 약관동의 패널**이 노출된다.
동의 → 인게임 `/인증` 코드 본인인증 → **해당 서버 화이트리스트 등록 + 아래 역할 부여**.
동의·인증한 서버에만 접속할 수 있다.

| 역할 | 부여 조건 | 화이트리스트 | 처리 코드 | 상태 |
|---|---|---|---|---|
| `인증유저` (= RPG 플레이어) | RPG 약관동의 + 인게임 `/인증` 코드 인증 | ZenonRPG 서버 | `modules/onboarding/panels.py` + `integrations/rpg_api.py` | 🟢 |
| `포로몬플레이어` | Zenon Mon 약관동의 + Zenon Mon 인게임 인증 | Zenon Mon 서버 | `modules/onboarding/panels.py` + `integrations/zenon_mon_api.py` | 🟢 봇 측 구현 |

> 본인인증(`/인증` 코드)은 닉네임 소유권 검증·사칭 방지를 위해 **서버별로 유지**한다(DL-131).
> 현행 `인증유저` 역할이 RPG 화이트리스트 역할에 해당한다(별도 역할 신설 없이 의미만 명확화).
> Zenon Mon은 동일 패턴(약관동의 → Zenon Mon `/인증` → Zenon Mon 화이트리스트)으로 처리한다.
> 서버 접속정보(IP) 채널은 해당 서버 플레이어 역할에게만 연다.

## 자동 지급 가능 여부 판정

`permissions.is_auto_grantable(role_key)`:
- 권한 역할 키(B) → **항상 False**
- 알림 역할 키(C) → True
- 운영 권한을 알림처럼 자동 지급하려는 시도를 코드 레벨에서 차단하는 가드.

## 보안 메모

- 운영 권한 역할 ID 는 `.env` 에서 로드한다(코드 하드코딩 금지).
- 봇이 멤버 역할을 변경할 때는 항상 reason 을 남긴다(감사 로그).
- 운영 명령어(역할부여·골드지급 등)는 실제 구현 전 설계/승인을 선행한다
  ([`domains/admin.md`](domains/admin.md)).
